# Implementation Plan: loop-versioning

Intent: inline — implement the loop-versioning design of
`docs/internals/loop-versioning.md` (an entry guard ahead of a header-cached
innermost `while`, a plain pointer loop when it holds, today's loop text when
it does not), with every behaviour today's loop has preserved. No
`.agents/compile/loop-versioning.yaml` exists; the constraints are gathered
here once:

- **Invariants.** Program output, raised exceptions (class and message), the
  partial state an exception leaves, and Float bits are what the current
  spinel produces, for every program; the decision is bisectable like every
  other decision whose wrong answer is a miscompile (`src/decide.c`).
- **Allowed blast radius.** `src/codegen_stmt.c`, `src/codegen_call_recv.c`,
  `src/codegen_call.c`, `src/codegen_internal.h`, `Makefile`,
  `tools/README.md`, `test/`, `docs/internals/loop-versioning.md`. No
  analysis change, no runtime (`lib/`) change, no new compiler flag.
- **Breaking-change posture.** Internal only: the emitted C is not a stable
  surface. No user-visible switch is added or removed.

Classification: **design** (measured hot path + a seam decision between
`emit_while`'s header-cache region and a separate pass). Runtime route: the
touched code is C with no language pack in the `$dev` router; validation is
repo-native (`make`). The `.rb` files touched are corpus fixtures, not gem
code, so `ruby-dev` adds nothing. Architecture branches loaded:
`deep-modules`, `performance`; axioms held throughout.

Evidence for every claim below lives in
[`loop-versioning/evidence/`](loop-versioning/evidence/) and is regenerated by
two scripts; nothing in this plan rests on the earlier `/tmp/simd` work.

### 1. Today's loop: scalar, and not even an innermost loop to LLVM

`gen/mm500.current.c` lines 341–344 is the j loop as `bin/spinel -S
--no-line-map` emits it (benchmark/bm_matmul.rb with `n = 500`):
`sp_int_add(sp_int_mul(lv_i, lv_n), lv_j)` index arithmetic (overflow-checked),
a `(unsigned long long)_t16 < _hcl2_0 ? _hcd2_0[_t16] : sp_FloatArray_get(...)`
read for `c` and for `b`, `SP_FLOAT_NIL_CK` on `aik * b[..]` and on the `+`,
and a store behind `_hcw2_0 && _t13 < _hcl2_0` whose else is
`sp_FloatArray_set(lv_c, _t13, _t14), _SP_HCR2()`. `gen/cc-argv.txt` records
that the C spinel compiles is this text exactly (its `#line` lines dropped:
`true` for every program) and the argv it uses:
`-O2 -Wno-all -ffunction-sections -fdata-sections -ffp-contract=off
-falign-functions=64 -falign-loops=64 -Werror=incompatible-pointer-types
-Werror=int-conversion -ferror-limit=0 -fno-show-column
-fno-caret-diagnostics -I<repo>/lib -I<repo>/lib/regexp
-DSP_INT_OVERFLOW_MODE_RAISE <c> <repo>/lib/libspinel_rt.a -lm
-Wl,-dead_strip`.

The asm (`gen/mm500.current.main_body.s`) shows the loop scalar: `ldr d0`,
`ldr d1`, `fmul d1, d8, d1`, `fadd d9, d0, d1`, `str d9` (lines 646–707), with
`cmp x15, x23` against `x23 = 0x7FF8000000000001` (lines 544–545) after every
load and after the product. No `.2d` instruction exists in the function
(`gen/mm500.asm-ir-summary.txt`: `fmul.2d 0`, `fadd.2d 0`, no `vector.*` IR
block).

**Correction to the design doc's reason.** "LLVM does not vectorize a loop
with early exits" is true but is not what happens first. The vectorizer emits
**no remark at all** for lines 341–344 (`gen/mm500.current.remarks.txt`): it
only looks at innermost loops, and this one is not. `sp_FloatArray_set`
(`lib/sp_array.h:138`) is inlined into the slow path, and its
`while (i >= a->cap) { ... sp_pl_realloc ... }` is a loop nested inside the
Ruby loop. The asm says so in LLVM's own loop comments: the Ruby loop's header
`LBB36_39` is "This Loop Header: Depth=3" (line 629), and the realloc loop is
"This Inner Loop Header: Depth=4" (lines 727–739). The diagnostic variant
`gen/mm500.diag-set-ool.c` moves only that call out of line; then the Ruby
loop is innermost and the vectorizer states its reasons
(`gen/mm500.diag-set-ool.remarks.txt`, lines 343–344): "Cannot vectorize early
exit loop with more than one early exit", "Control flow cannot be substituted
for a select", "value that could not be identified as reduction is used
outside the loop". Either way the fix is the same: the fast loop has no slow
path in it at all.

### 2. The versioned shape vectorizes; LLVM checks the overlap itself

`evidence/prototype.rb` is the hand-written prototype: it rewrites the C that
spinel emitted, inserting ahead of each recognised cached loop the entry guard
the design describes (generated from per-kernel facts: arrays read/written,
each array's offset `B`, the bound `N`, the nullable Float locals) and a
hand-written fast statement, keeping today's loop text unchanged as the else
arm. The matmul result is `gen/mm500.versioned.patch` (a `diff -u` against
`gen/mm500.current.c`); it adds 30 lines and removes none.

At spinel's exact flags: `mm500.versioned.c:367: remark: vectorized loop
(vectorization width: 2, interleaved count: 4)`
(`gen/mm500.versioned.remarks.txt`). With `-fno-vectorize -fno-slp-vectorize`
the same file stays scalar (`gen/mm500.versioned-novec.remarks.txt`,
`fmul.2d 0` in the summary). No `restrict`, no `-march`.

The overlap check is in the IR (`gen/mm500.versioned.ir-excerpt.ll`):
`%bound0 = icmp ult ptr %42, %scevgep367`, `%bound1 = icmp ult ptr %43,
%scevgep`, `%found.conflict = and i1 %bound0, %bound1`, branching to the
scalar loop on a conflict and to `vector.ph` otherwise; the vector body's
`c` accesses carry `!alias.scope !205, !noalias !208`, valid only because of
that check. In the asm (`gen/mm500.versioned.asm-excerpt.s`) the guard's
`_hcw` / `B + N <= len` / `aik` nil tests (lines 2–13), then the two range
compares (lines 15–27), then the loop `LBB36_87` with `ldp q`, `fmul.2d v4,
v4, v16[0]`, `fadd.2d`, `stp q`.

Because `bm_matmul`'s `n` is a literal and `sp_matmul` is inlined into
`main`, clang knows the trip count here (`icmp eq i64 %index.next, 496`). The
variant `gen/mm500.versioned-runtime-n.c` reads `n` from the environment: it
still vectorizes (width 2, interleave 4, line 367) and the check then appears
as its own `vector.memcheck` block (`gen/mm500.asm-ir-summary.txt`).

Aliasing is exercised, not only claimed: `fixtures/lv_alias.rb` runs
`matmul(m, m, n)`, `matmul_into(c, c, c, n)` (the written array read under
two other names) and `axpy(v, v, 20, oy, ox, 0.5)` with distances +1 (a
loop-carried dependence through one array), −1 and +3 (under one 4-element
interleave group). The prototype took the fast arm every time ("matmul-inner
fast x32, axpy fast x4") and its output equals today's spinel and CRuby
(`gen/fixtures.txt`).

### 5. Float reductions: refuted — they vectorize, in order, bit-identically

`fixtures/dot.rb` is the spectral_norm-shaped reduction
`sum = sum + x[j] * y[j]` over terms spanning ~20 orders of magnitude, so a
reordered sum shows in the printed bits. With the prototype's hoisted checks
and spinel's flags, clang **does** vectorize it:
`dot.versioned.c:319: remark: vectorized loop (vectorization width: 2,
interleaved count: 4)` (`gen/dot.versioned.remarks.txt`). The IR
(`gen/reduction.txt`) shows how: the products are `fmul <2 x double>`, and the
sum is a chain of `call double @llvm.vector.reduce.fadd.v2f64(double %acc,
<2 x double> ...)` **without** `reassoc` — LLVM's ordered (strict) reduction.
The asm shows it lowered to lane-by-lane scalar adds in source order
(`fadd d0, d8, d0; fadd d0, d0, d4; fadd d0, d0, d1; ...`). The printed sum
and its bits (`c2221e007772845f`) are CRuby's in the current build, the
versioned build, and the versioned build with `-ffp-contract=on`. Only
`-fassociative-math -fno-signed-zeros -fno-trapping-math` reassociates (IR
`fadd reassoc nsz <2 x double>` into partial sums) and changes the result
(`-38906379193.258286`, bits `c2221e007772843e`).

So the doc's reason for leaving reductions out is wrong: the vectorizer keeps
the order by default (what protects CRuby's result is the absence of
reassociation flags, which spinel never passes, not `-ffp-contract=off`).
The timing ([Benchmarks](#benchmarks)) adds the other half: an ordered
reduction gains **nothing** from being vectorized here (the adds stay one
serial chain; `dot versioned` / `dot versioned -fno-vectorize` = 1.00x in both
sessions), while hoisting the checks out of it gains 1.65x. Reductions belong
in scope for the hoisting, not for the vectorization.

The doc also names `bm_spectral_norm`'s inner loop as the reduction example.
That loop is not header-cached at all: it calls the user method `eval_a`,
which `hc_call_ok` refuses (`gen/citations.txt`: one cached loop in the
program, and the inner loops read `sp_eval_a(...)` and `sp_FloatArray_get`).
Loop versioning cannot reach it without inlining, which is out of scope.

### 6. The nil sentinel: generated NaNs never collide; propagated ones can

`nan_check.c`, built with spinel's flags and run here (`gen/nan_check.txt`):
FPCR is `0x0` (default-NaN mode off, so NaN payloads propagate). Every NaN an
operation *generates* from non-NaN operands (`0/0`, `inf-inf`, `0*inf`,
`sqrt(-1)`, `fmod(1,0)`, `log(-1)`) is `0x7ff8000000000000`, never
`SP_FLOAT_NIL_BITS` (`lib/sp_types.h:124`). But a NaN operand propagates its
payload, and two non-nil inputs reach the sentinel exactly:

- a signaling NaN with payload 1 (`0x7FF0000000000001`): any arithmetic
  quiets it to `0x7ff8000000000001` (`sNaN + 0.0`, `sNaN * 1.0`, and the same
  through a vectorized `fadd.2d`/`fmul.2d` loop);
- `0xFFF8000000000001` (the sentinel with the sign set): `-x` and `x.abs`
  clear the sign and give the sentinel.

A Ruby program can only build these bit by bit (`pack`/`unpack`, binary I/O).
`fixtures/nan_payload.rb` shows today's spinel already treats the result as
nil where CRuby has a NaN (`gen/fixtures/nan_payload.spinel.out`: `nil`, then
"can't convert nil into Float (TypeError)", exit 1;
`gen/fixtures/nan_payload.ruby.out`: `NaN`, exit 0). What the fast loop
changes is where that existing divergence surfaces. Reasoned from the emitted
checks, not run: with an sNaN-payload-1 element in `b`, today's loop raises
TypeError at the `*` (its `SP_FLOAT_NIL_CK` sees the sentinel as the product),
while the fast loop stores the sentinel into `c` and the program sees a nil
element later. Neither matches CRuby. The design keeps the fast loop and
widens the documented compromise (the sentinel is a reserved bit pattern,
`lib/sp_types.h:118–123`) to say that arithmetic on such a crafted NaN may
yield it; the doc's sentence "arithmetic on non-nil values never produces
`SP_FLOAT_NIL_BITS`" is replaced. x86-64 also quiets signaling NaNs by setting
the same bit; that is from the architecture manuals, not measured here.

### 8. The seam: emit-time state — yes; `g_stmt_prev` — not the reason

`gen/citations.txt` (rg output with line numbers):

- `g_stmt_prev` is set per statement list entry (`src/codegen_stmt.c:13537`,
  `13599`, `13615`) and read by `emit_while` (`:6746`). It is only "the
  previous sibling in a `StatementsNode`", an AST fact any pass can compute;
  it does not by itself force the decision into `emit_while`.
- What does: the cache's entry table is filled **during body emission** — the
  access sites call `hc_array` / `hc_array_nilfree` (`src/codegen_call_recv.c:1694`,
  `src/codegen_stmt.c:2071`, `:14845`, `:15343`), which call `hc_entry`
  (`:6563`), which renders the receiver's C text then and there through
  `emit_expr` (`hc_recv_text`, defined `:6508`, called `:6566`). The guard must name those entries
  (`_hcdN_e`, `_hclN_e`, `_hcwN_e`), so it can only be written after the body
  has been emitted once, inside `hc_close`'s frame.
- The region nests through `g_hc` (`:6401`), and a loop inside a cached one is
  not cached (`use_hc = !sv_hc && ...`, `:6803`); polls depend on
  `g_uses_threads` / `g_uses_finalizers` (`polls_in_cond`, `:6828`). All
  emit-time.
- Emitting one node into more than one place is established practice
  (`src/decide.c:26`: "codegen emits one node into several inline sites and
  into buffers it later throws away"), so emitting the body twice (fast and
  today's) is not a new hazard class.

## Benchmarks

**Method** (`evidence/bench.rb`). The binaries are the ones `regen.rb` built;
each session first runs every variant once and checks its stdout
(`bench/<s>/output-check.txt`, with each binary's sha256), then discards 3
warm-up rounds and runs 40 rounds. A round runs the ten variants in a fixed
order (A B C ... A B C ...), so slow drift hits every variant alike. Each
sample is the wall time from `CLOCK_MONOTONIC` around spawn-and-wait (process
start included), plus the child's user and sys time; every sample is in
`bench/<s>/samples.csv` (400 rows). Quartiles use linear interpolation; IQR is
q3 − q1. After both sessions, `regen.rb` was run again and rebuilt the ten
benchmarked binaries byte for byte (`shasum -a 256 -c`: all `OK`), so the
measured binaries are the ones the scripts produce.

`mm500` is benchmark/bm_matmul.rb with `n = 500` (its normal output, no
dump); `dot` is the reduction kernel over 100,000 elements, called 1,000
times (`gen/dotbench.rb`); `startup` is `puts 1`. "versioned
-fno-vectorize" is the same versioned C built with `-fno-vectorize
-fno-slp-vectorize` added: the checks are hoisted but the loop stays scalar.
That isolates the two effects.

| dot current (spinel) | 148.88 | 147.65 | 2.79 (148.31–151.10) | 148.60 | 147.62 | 0.76 (148.30–149.06) |
| dot versioned -fno-vectorize | 90.26 | 89.56 | 1.23 (90.01–91.25) | 90.12 | 89.52 | 0.95 (89.95–90.90) |
| dot versioned | 89.98 | 89.28 | 0.70 (89.73–90.43) | 89.98 | 89.29 | 0.69 (89.72–90.41) |

The sessions agree: the largest median difference is 1.1% (startup, 0.03 ms);
every mm500 and dot median differs by ≤ 0.3%. Ratios of medians, s1 / s2:

| Split | s1 | s2 |
| ----- | -: | -: |
| matmul: hoisting the checks (current / versioned -fno-vectorize) | 5.13x | 5.11x |
| matmul: vectorizing (versioned -fno-vectorize / versioned) | 1.98x | 1.98x |
| matmul: both (current / versioned) | 10.14x | 10.14x |
| reduction: hoisting the checks | 1.65x | 1.65x |
| reduction: vectorizing | 1.00x | 1.00x |
| spinel's own build / direct cc build of the same C | 1.00x | 1.00x |

So for matmul most of the gain comes from removing the per-element checks
(222 → 43 ms), and vectorization then halves what is left (43 → 22 ms). For the
ordered reduction, only the hoisting counts. The direct cc build times the
same as spinel's binary, so compiling the extracted C directly does not skew
the comparison. These numbers supersede the earlier `/tmp/simd` figures
(263 / 55 / 31 ms, conditions unknown).

**Why n = 150 is unusable for this.** `puts 1` alone takes 2.64 ms. At n =
150 the versioned program takes 3.20 ms, so its kernel and setup together are
about 0.56 ms above startup. That matches the n = 500 run scaled by n³
((21.93 − 2.64) × (150/500)³ = 0.52 ms; for the current build, 5.93 ms
predicted vs 6.01 ms observed). The same scaling puts the scalar versioned
build at about 1.10 ms above startup. A difference of about 0.58 ms is visible
in medians of 40 runs, but the split cannot be read off. Raw times compress
it: about 3.7 ms vs 3.2 ms reads as 1.18x where the kernel ratio is 1.98x.
Recovering the kernel ratio means subtracting a startup estimate whose own
spread (IQR 0.16 ms, max − min 0.9 ms) is about 30% of the 0.52 ms being
measured. The headline is compressed the same way: 2.7x at n = 150 against
10.1x at n = 500. At n = 500, startup is about 12% of the fastest variant
and about 1% of today's build. The current n = 150 build is *not* dominated by
startup (6 of its 8.65 ms are the kernel); the versioned one is.

## Design changes the evidence forces

1. **Reductions are in scope.** The fast loop for `s = s + <expr>` is
   emitted like any other; clang keeps the additions in order (claim 5), and
   the measured win is the hoisted checks (1.65x), not vectorization (1.00x).
   The "Float reductions" bullet moves from *Out of scope* to the design, with
   the invariant stated: spinel never passes a reassociation flag
   (`-ffast-math`, `-fassociative-math`), and the fast loop's arithmetic is the
   same operations in the same order. Making a reduction *faster than that*
   would need reassociation, which stays out of scope because it changes the
   result (`gen/reduction.txt`).
2. **Induction step.** The motivating benchmark writes `j = j + 1`, which is a
   `LocalVariableWriteNode`, not the `j += 1` (`LocalVariableOperatorWriteNode`)
   that `hc_bounded_index` accepts (`src/codegen_stmt.c:6658`). The shape test
   accepts both, or bm_matmul never qualifies.
3. **Marked arrays do not qualify.** `may_nil` is kept up to date only for
   arrays analysis did *not* mark: "A marked array's whole-array reads scan
   for the sentinel, as its stores set no flag" (`src/analyze.c:24372`). Every
   array in the loop must pass `!nullable_int_elem_array(c, recv)`; the
   run-time `SP_MAY_NIL` test is only sound for those. (A Float array with a
   stored nil becomes a `PolyArray` anyway — `lv_nil_stored.rb` — but an
   `IntArray` can be marked and stay typed.)
4. **A fifth emit site.** The doc lists the read, the `[]=` store, the `op=`
   store and `emit_nilfree_operand`. The `SP_FLOAT_NIL_CK` on `c[..] + aik *
   b[..]` comes from none of them: it is the binary Float operator in
   `src/codegen_call.c:13255–13304`, gated by `cmp_operand_may_be_nil`
   (`src/codegen_call.c:1631`). The fast loop's nil-freedom is answered there.
5. **Bisectable.** Loop versioning drops checks whose wrong omission is a
   miscompile, which is what the decision registry exists for
   (`src/decide.c:1–41`). It gets a kind, `loop-version`, keyed at the `while`
   node, listed in `DECISION_KINDS` and `tools/README.md`, with a fixture in
   `DECISION_TESTS` (the `decisions-test` leg fails a kind no program's C
   changes under).
6. **NaN caveat documented** (claim 6), not guarded: the only inputs that
   reach the sentinel are crafted NaNs, today's code already mishandles them,
   and a guard for them would scan every element.
7. **`may_nil` is array-wide and sticky.** One gap anywhere sends every entry
   of the loop to the slow arm (`lv_nil_elem`: slow x3). Accepted; noted in the
   doc so nobody reads a missing speed-up as a bug.

## Seam decisions (architecture)

- **Where the decision lives.** In `emit_while`, inside the existing
  `HcRegion` / `hc_close` frame; *rejected:* a separate pass after
  `repr_seal`, because the cache's entry table and each receiver's C text
  exist only during emission (claim 8), so a pass would re-derive both — a
  second owner of `hc_node_ok`'s and `hc_recv_text`'s answers.
- **Who owns "this operand is nil-free in the fast loop".** One predicate on
  the region (`hc_fast_nilfree(c, node)` next to `hc_array_nilfree`): true for
  a read of a cached array at a vetted index, a guarded local, a literal, or
  arithmetic over those. `cmp_operand_may_be_nil` and `emit_nilfree_operand`
  ask it while the region is in fast mode; *rejected:* a fast-loop flag tested
  separately at each of the five sites, which would make five owners of one
  fact.
- **How the fast body is emitted.** Through the normal statement and
  expression emitters, with the region in fast mode: the access sites emit
  `_hcdN_e[_lvoN_e + lv_j]`, the nil predicate answers as above, and
  non-index Int arithmetic keeps its overflow helpers; *rejected:* a dedicated
  mini-emitter for the fast body, which would duplicate Ruby arithmetic
  semantics (Int/Float coercion, overflow helpers, floored division) — dual
  ownership of the operators.
- **Who owns each offset `B`.** The guard: a small emitter for the offset
  grammar (Int literals, locals the loop does not assign, `+ - *`) that writes
  `__builtin_{add,sub,mul}_overflow` chains into `_lvoN_e`; the fast access
  sites read `_lvoN_e`, never recompute `B`. *Rejected:* reusing
  `emit_int_expr` for `B` in the guard, whose `sp_int_mul` raises on overflow
  instead of failing the guard.
- **What the fast-mode state is.** Fields on `HcRegion` (the induction local
  and bound, the `(entry, offset node, _lvo name)` table, a `fast` flag),
  nothing global beyond the existing `g_hc`. Deletion test: removing the
  feature is removing those fields, `hc_versioned_shape`, the guard emitter,
  and one `if (g_hc && g_hc->fast)` per access site.

Performance stop rules (architecture `performance`): the bottleneck class is
evidenced (per-element branch and check overhead, then data-parallel FP
throughput), the intended path is shown to run (remarks, IR, asm), and the
end-to-end budget is measured; no intrinsics, `restrict` or `-march` are
earned by this evidence.

## Phase 02 — Version single-threaded header-cached loops behind an entry guard

## Risks, non-goals, follow-ups

- **The machine.** Benchmarks ran on a fanless MacBook Air M2 that its owner
  was using during this work (Xcode builds, Spotlight, a Time Machine backup,
  Podcasts). Each session started on a passing idle check, and both failed
  their after-checks (see [Benchmarks](#benchmarks)). The two sessions, 13
  minutes apart, agree to ≤ 0.3% on every kernel median, but nothing
  guarantees the machine was unused while they ran. A fanless machine also
  throttles under sustained load; each session lasted about 35 s, and the
  after-checks report no thermal or performance warning.
- **Prototype ≠ compiler.** The prototype's fast statements are hand-written
  per kernel and recognised by text (`prototype.rb`'s `KERNELS`); the guard is
  generated the way Phase 02 will generate it. Phase 03 re-measures the real
  build; a gap to the prototype's numbers is a finding, not noise.
- **Constant trip count.** bm_matmul's `n` is a literal and is inlined; the
  run-time-`n` variant shows vectorization does not depend on it, but it was
  not timed.
- **Phase 04's fixture is timing-dependent.** A second thread shrinking the
  array "mid-loop" is not deterministic in CRuby either. The fixture should
  assert only what every interleaving shares (no crash; the result is one of
  today's outcomes) and run under `gc-stress-test`'s budget; if that cannot be
  made reliable, Phase 04 ships with the threaded legs as its only proof and
  says so.
- **Crafted NaNs** (claim 6): a known, documented divergence, moved not
  created.
- **Out of scope (unchanged):** intrinsics, `restrict`, `-march`. **Follow-up**
  (the doc's phase 3, not planned here): `spinel-doctor`'s advice leg naming
  why a loop did not qualify; widening the index shapes only for a measured
  kernel.
- **Observability:** the decision log (`--decisions-log`) lists every loop
  versioned; no runtime logging is added to the hot path.
- **Security:** no boundary or capability change; the guard's overflow
  checks are what keep the raw indexing in bounds, and the `lv_index_overflow`
  and `lv_short_array` fixtures pin that.
